# 동사 형태 확장 논의 메모

2026-09-17. Step 2 · Lesson 2에서 테형을 배우기 시작한 시점의 논의다. 다음에 이어서 검토하기 위한 기록이며, 구현을 확정한 기획서는 아니다. 동사 형태 기능과 아래 예문 생성 정책은 아직 구현하지 않았다.

## 하고 싶은 것

J-VOCA는 짬짬이 사용하는 단어장이다. 별도의 문법 훈련 앱으로 만들기보다, 기존 단어장을 보면서 테형·타형과 앞으로 배울 활용형도 자연스럽게 익히고 싶다.

기본 화면에서는 등록한 단어를 그대로 보여주고, 사용자가 동사 형태를 선택하면 동사의 표기·읽기·발음과 예문도 그 형태에 맞게 바뀌는 방향을 논의했다. 예를 들어 `行く → 行って → 行った`다. 명사는 그대로 두고, 단어 수와 복습 대상도 늘리지 않는다.

## 공감한 방향

- 형태 선택은 자주 쓰는 학습 화면에서 접근할 수 있으면 좋겠다. 복습 목록의 제목 아래, 전체 복습 카드 위에 `동사 형태: 기본` 선택기를 두는 안을 이야기했다. 정확한 위치, 단어 탭·열람·듣기와의 적용 범위, 마지막 선택 저장은 구현 때 정할 사항이다.
- 평가는 기존처럼 **단어 자체에 대한 모름/애매/앎**으로 유지한다. 형태별 FSRS 상태나 별도 평가 기록을 만들지 않는다.
- 평가 기준을 설명하는 상시 안내나, 카드 뒷면에 기본형·기본 뜻을 항상 표시하는 장치는 필요하지 않다. 개인 학습용 앱의 기준으로 정리하면 된다. 반드시 README에 적어야 한다는 뜻도 아니다.
- 선택한 형태에 맞는 예문과 번역이 필요하다. 다만 테형은 문맥에 따라 뜻이 달라지므로 `行って = 가서`처럼 뜻을 고정하지 않는다. 예문 번역을 중심으로 보여주는 안을 논의했으며, 카드 앞·뒷면과 한→일 복습에서 뜻을 어떻게 표현할지는 미정이다.
- 현재 등록 데이터에는 사전형 외에 마스형과 구 단위 표현도 있다. ‘기본’이 모든 단어의 사전형을 뜻한다고 가정하면 안 된다.

## 예문 생성에 대한 현재 방향

앱을 오래 켜 두고 예문을 생성하는 방식은 사용 목적에 맞지 않는다. 무료 쿼터와 처리 시간도 고려해야 하므로, 예문은 앱 밖에서 미리 준비하고 앱은 받아서 보여주는 방향이다.

매일 예문을 교체할 만큼 자주 복습하지는 않는다. 따라서 GitHub Actions의 정기 실행은 유지하더라도, **등록일 기준 최근 7일 이내의 단어 중 필요한 예문이 없는 경우만 채우는 것**으로 범위를 좁혔다.

- 기본 예문이 있고 테형 예문만 없으면, 테형 예문만 생성한다.
- 필요한 예문이 이미 있으면 유지한다. 생성일이 어제라는 이유로 교체하지 않는다.
- 등록 후 7일이 지난 단어까지 채우는 전체 마이그레이션은 하지 않는다.
- 이미 만들어진 예문은 7일이 지나도 계속 사용한다.
- 오래된 단어에 선택한 형태의 예문이 없다면 활용형 표기·읽기만 보여주고 예문 영역을 생략하는 안을 제안했다. 이때 뜻을 표시하는 방식은 더 검토해야 한다.
- 단어 수정으로 기존 예문이 현재 표기·읽기·뜻과 맞지 않는 경우의 처리도 필요하다. 현재 앱은 이런 예문을 숨긴다. 최근 7일 제한 밖까지 재생성 범위를 넓히자는 합의는 없었다.

현재 구현은 최근 등록 단어의 예문을 하루 한 번 교체한다. 위 내용은 변경하려는 방향이며, 실제 동작과 구분해야 한다.

기존 데이터 구조도 함께 살펴봤다. `words.json`이 단어 원본이고, `sentences.json`의 `source`는 예문을 만들 당시의 표기·읽기·뜻을 보관하는 스냅샷이다. 단어를 수정한다고 함께 덮어쓰는 값이 아니라, 현재 단어와 비교해 오래된 예문을 숨기는 기준으로 사용한다. 형태별 예문으로 확장할 때도 이런 유효성 확인이 필요하다.

## 아직 해결하지 못한 핵심: 새 형태를 어떻게 추가할까?

형태를 배울 때마다 기능 개발과 예문 생성을 일일이 요청하는 것은 번거롭다. 그렇다고 앞으로 배울 모든 문법과 예문을 한꺼번에 만들어 둘 필요도 없다.

다음 방법을 검토했지만 만족할 만한 방법을 정하지 못했다.

| 검토한 방법 | 남은 문제 또는 사용자 의견 |
|---|---|
| 교재 목차·주요 학습 내용을 미리 등록하고 진도에 맞게 활성화 | 앱의 개인 진도를 GitHub Actions와 동기화해야 하는 구조가 어색하다. 진도의 기준과 관리 위치도 미정이다. |
| 앱에서 활용형과 예문을 동적으로 변환 | 단어 활용은 규칙으로 처리할 여지가 있지만, 자연스러운 예문과 번역을 단순 치환하기는 어렵다. |
| 앱에서 AI 예문 생성 후 캐시 | 앱을 오래 실행해야 하고, 무료 쿼터와 처리 시간이 부담이므로 사용 목적에 맞지 않는다. |
| 저장소에 예문 생성 대상 형태 목록을 두기 | Action 처리 자체는 단순해지지만, 누가 언제 목록을 바꾸는지와 반복적인 수작업 문제를 해결하지 못했다. 사용자는 아직 좋은 방법이라고 판단하지 않았다. |

마지막으로 제안했던 저장소 목록 방식은 다음과 같다. **채택된 설계가 아니라 다음 논의의 출발점**이다.

```json
{ "sentenceForms": ["base", "te"] }
```

목록에 `ta`를 넣으면 Action은 매 실행 때 최근 7일 이내 단어와 대상 형태를 확인하고 없는 예문만 생성한다. 별도의 ‘형태 추가 이벤트’를 추적할 필요는 없다. 하지만 타형을 준비하기 시작할 시점은 목록을 바꾸는 누군가가 정해야 한다. 앱에서 형태를 선택하는 행위와 이 목록의 변경은 별개다.

## 다음에 이어서 정할 것

1. 형태의 지원·예문 준비·화면 노출을 언제, 어디서 관리하면 매번 개발을 요청하지 않아도 되는가?
2. 앱 진도를 Action에 동기화하지 않으면서 교재 목차·주요 학습 내용을 활용할 수 있는가?
3. 단어 활용 규칙과 예문 문법 범위를 어떻게 나눌 것인가? 테형 예문이라고 해서 아직 배우지 않은 구문까지 자동으로 허용할 것인가?
4. 문맥에 따라 달라지는 뜻, 예문이 없는 형태, 한→일 복습을 각각 어떻게 표시할 것인가?
5. 실제 구현 시 동사 분류·예외·구 단위 표현, 형태별 예문 저장, 구버전 앱 호환성을 어떻게 다룰 것인가?

구현할 때는 단어별 평가 기록을 보존해야 한다. 현재 예문은 단어 ID와 날짜로 저장되므로 형태를 추가하려면 JSON과 IndexedDB 구조를 함께 검토해야 한다. 기존 예문도 항상 사전형으로 작성된 것은 아니므로, 이를 엄격한 ‘사전형 예문’으로 일괄 분류해서는 안 된다.

참고했던 서비스는 Bunpro의 [Kaijugation](https://kaijugation.bunpro.jp/levels), [MaruMori](https://marumori.io/), [Steven Kraft의 활용 연습](https://steven-kraft.com/projects/japanese/randomize/)이다. 별도 활용 연습이나 형태별 평가를 그대로 도입하기보다는, J-VOCA의 단어장 사용 흐름에 맞는 방식을 찾고 있다.
